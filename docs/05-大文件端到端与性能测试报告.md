# 05 - 10GB 大文件端到端验证与性能测试报告

> 测试日期：2026-09-20 ｜ 对象：`testdata/alert_dlscdb1.log`（真实 Oracle alert 日志）
> 方式：release 二进制实跑 + 外部工具（GNU grep / wc）交叉校验 + 独立取样脚本取证
> 原则：**源日志全程只读**，所有写操作仅落在 `.perf/`（已 gitignore）

---

## 一、结论摘要

本次真机验证在**功能正确性**与**资源红线**上给出了正面结论，但也暴露出两个**足以让核心用例失效的缺陷**。

| 维度 | 结论 |
|---|---|
| 内容检索正确性 | ✅ 与 GNU grep 逐条计数完全一致（15,608 / 15,608） |
| 行数统计正确性 | ✅ 与 `wc -l` 完全一致（180,270,057） |
| 内存红线 | ✅ 峰值驻留 18.9–21.3 MB，**远低于** 192 MiB 软上限 |
| 内容检索吞吐 | ⚠️ 328 MiB/s，为 GNU grep 的 48%（待优化） |
| **时间切片内容完整性** | ❌ **仅返回 3.58% 的目标内容，丢失 96.42%** |
| **稀疏定位** | ❌ **完全未接线**，0.22% 的窗口也全量扫 10GB |

**一句话**：这个工具能正确地把整份日志读一遍、把关心的行挑出来、内存控制得极好；但针对 Oracle alert 这类「时间戳独占一行」的多行日志，时间切片返回的结果基本不可用，而且它的稀疏定位引擎还没接上，每次都是暴力全扫。

## 三、测试环境与方法

- 二进制：`go build -trimpath -ldflags="-s -w"`（3.3 MB），Go 1.25.10，Windows amd64
- 计时：`.NET Stopwatch` 包裹进程生命周期
- 内存：进程退出前按 200ms 采样 `WorkingSet64` / `PeakWorkingSet64`
- 交叉校验：GNU grep 与 `wc -l`（Git for Windows 自带）
- 每轮次均在**无其它大 IO 作业**时进行，避免相互干扰

> 注：首次 `slice` 测得 232s，当时有 Python 取样作业并发；隔离后复测得 156s。**后续一律采用隔离后的 156s 作为基线**。这说明本机 IO/CPU 争用对结果影响可达 48%，任何性能对比都必须控制变量。

### 4.3 ❌ 时间切片：丢失 96.42% 的目标内容

对窗口 `[2026-09-12 00:00:00, 2026-09-13 00:00:00)`：

| 口径 | 行数 |
|---|---|
| 应得（时间戳继承语义，ground truth） | **436,251** |
| 实得（logseek 输出） | **15,641** |
| 丢失 | **420,610（96.42%）** |

落到文件里更直观——`slice_1d.txt` 的 15,641 行全部是这样的内容：

```
Sat Sep 12 00:00:00 2026
Sat Sep 12 00:00:00 2026
Sat Sep 12 00:00:10 2026
...
```

**只有光秃秃的时间戳，真正的报错与上下文一行都没留下。**

根因在 `internal/domain/timeslice/timeslice.go:83-92`：

```go
func (f *Filter) Accept(line []byte) bool {
	f.Scanned++
	t, err := timefmt.ParseLine(f.Layout, string(line))
	if err != nil {
		f.BadLines++              // ← 续行无时间戳，一律计为坏行丢弃
		return !f.Policy.DropBadLines
	}
	return !t.Before(f.Window.Start) && t.Before(f.Window.End)
}
```

过滤器逐行独立解析时间，遇到续行即判为坏行。本次跑出来的 `bad_lines = 172,389,878` 正是被丢弃的续行总数。

### 4.4 ❌ 稀疏定位：零接线

窗口只占全文件的 **0.22%**（23.7 MB / 10,842 MB），但工具扫了全部 180,270,057 行、耗时 156 秒。

全仓核查 `timeslice.Locate` 的调用点：

```
internal/application/application.go:76:   timeslice.RelativeWindow(...)   ← 只有相对时间解析
internal/application/application.go:86:   timeslice.New(...)              ← 只有过滤器
# Locate 无任何调用点
```

`Export` 的执行路径始终是「打开文件 → 从头扫到尾」，从不把 `Locate` 算出的 `[StartOff, EndOff)` 拿来裁剪扫描范围。这与审查报告 04 里 `MaskWriter` 的「造而不用」是同一类问题。

### 4.5 已修复：预检探针的两处缺陷

测试中发现并已修复（提交 `44c8f42`）：

| 缺陷 | 表现 | 根因 |
|---|---|---|
| 尾部样例错位 | 展示的 5 行与文件真实末尾**完全不符** | `tailLines` 取的是尾部窗口「前 15 行中的后 5 行」 |
| 末条时间为空 | 明明「可时间切片」，`末条时间` 却是空白 | 只对样例最后一行尝试解析，而该行是续行 |

修复后与 ground truth 完全一致：末条时间 `2026-09-20 09:15:26`，尾部样例与 `tail -5` 逐字节吻合。新增的 3 条回归用例均已验证「对旧实现 FAIL、对新实现 PASS」。

## 五、性能测试

### 5.1 吞吐基准

| 负载 | 吞吐 | 相对 GNU grep |
|---|---|---|
| GNU `grep -c`（C 实现，基准） | **684.3 MiB/s** | 100% |
| logseek 内容检索 | **328.7 MiB/s** | 48% |
| logseek 时间切片 | **66.2 MiB/s** | 9.7% |

时间切片比内容检索慢 **5 倍**，原因是每条线都要走一次 `timefmt.ParseLine`——180M 行的时间解析成本远超过 AC-FSM 字节匹配。这是当前最大的性能瓶颈。

### 5.2 内存表现（亮点）

| 负载 | 峰值驻留内存 |
|---|---|
| 内容检索 | **18.9 MB** |
| 时间切片 | **21.3 MB** |

面对 10GB 文件，峰值内存稳定在 20 MB 上下，**仅为 192 MiB 软上限的 11%**。流式分块读取 + 单行缓冲的设计在这里经受住了真实验证，未出现随文件大小增长的内存爬升。

### 5.3 落盘对性能的影响

| 对比组 | 不落盘 | 落盘 | 差异 |
|---|---|---|---|
| 内容检索（15,608 行） | 31.50s | 31.46s | **无显著差异** |
| 时间切片（15,641 行） | 156.19s | 156.36s | **无显著差异** |

写入量小时，`bufio` 缓冲 + 结果追加的开销被 IO 等待掩盖，可以忽略。

### 5.4 ⚠️ 高命中率下的写放大

一次实验性测试（关键词 `LOGMINER`，命中率超过 50%）在 **20 分钟内未跑完**，输出文件已增长到 **5.48 GB** 且仍在写入，为控制磁盘占用而中止。

这说明当命中率很高时，**写入路径会成为新的主导开销**（且每行还要额外过一遍脱敏正则）。生产环境用泛化关键词做大文件导出时需要注意，建议先加时间窗口收敛范围。

## 七、修复建议

**F3（最高优先级）**——引入时间戳继承（sticky-time）语义：续行沿用上一个已知时间戳参与窗口判断。

关键点：对「每行都带时间戳」的普通日志，该语义**不产生任何副作用**，因此可以安全地作为默认行为。建议实现为 `Policy` 上的开关（默认开启），并补 `--sticky-time/--no-sticky-time` 命令行开关以备特殊场景。预期收益：修复后同一窗口应输出 436,251 行而非 15,641 行。

**F4**——在 `Export` 中接入 `Locate`：先用稀疏二分求出 `Span`，若 `Mode == SpanSeek` 则只扫 `[StartOff, EndOff)`，否则保持全扫。预期收益：0.22% 的窗口从 156 秒降到亚秒级。

**F5**——性能瓶颈定位后优化 `ParseLine`（如按布局快速预筛首字符、复用缓冲区）。

## 八、可复现命令

```bash
# 编译 release 二进制
go build -trimpath -ldflags="-s -w" -o bin/logseek.exe ./cmd/logseek

# 预检（应 <1s）
./bin/logseek.exe inspect testdata/alert_dlscdb1.log

# 检索并交叉校验
./bin/logseek.exe grep testdata/alert_dlscdb1.log -k ORA-00600 --json
grep -c ORA-00600 testdata/alert_dlscdb1.log

# 时间切片
./bin/logseek.exe slice testdata/alert_dlscdb1.log \
  --start "2026-09-12 00:00:00" --end "2026-09-13 00:00:00" -o out.txt --json

# 行数校验
wc -l testdata/alert_dlscdb1.log
```

> ⚠️ 复现 F3 时请勿使用高命中率关键词直接落盘（见 5.4），否则会产生数 GB 输出文件。
